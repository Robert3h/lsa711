The growth-rate trap in M&A: at which layer should the data be merged?

The problem: a company "grew", but not on its own

In peer comparison, the trap most easily overlooked is M&A.

Suppose a brokerage acquires another during the period. If you compare its "post-merger size" directly with "itself before the merger", the growth rate is badly overstated: it looks like strong growth, but most of it was bought. An executive judging the competitive landscape on that number will reach a skewed conclusion.

The principle: pro forma consolidation

The answer is the familiar financial practice of pro forma consolidation: when comparing, every past period is treated as if the merger had already happened, adding up the historical figures of the acquirer and the acquired. With both periods on the same base, what you see is real growth.

The principle is simple; the hard part is which layer of the system to do it in. I have used two approaches in practice, each suited to its own situation.

Approach 1: merge in the calculation layer (parameter switch)

The database stores only the original figures of legally separate companies, and the merger logic lives in the calculation layer: a mapping table states "who merges into whom, from which period", plus a switch. Flip the switch and every related formula moves to the merged basis together, about 8,000 formulas at once.

  • Pros: full detail is preserved; the same data can produce both "pre-merger" and "post-merger" versions, convenient for disclosure and reconciliation.
  • Cost: every additional acquired firm makes the mapping rules more complex and every recalculation slower.

The mapping table has one more advantage: it can be prepared in advance. As soon as a deal is announced, even before it takes effect, I register it in the mapping table with a disable flag so it stays out of the calculations for now. In the month it takes effect I simply remove the flag and the merged basis applies, without touching a single formula. In software engineering this is called a feature flag: ship the change into the system first, then use a switch to decide when it goes live.

This approach suits one-to-one mergers, and situations where both versions must be shown side by side and reconciled repeatedly.

Approach 2: merge in the load layer (sum first, then store)

Later a different situation arose: one peer acquired more than one firm. Staying with approach 1 would have expanded the mapping rules from "A = A + B" to "A = A + B + C + …", with more complex formulas and slower calculation, all to keep detail that executives almost never look at.

So this time I moved the merger up to the load layer: before the data enters the database, the acquired firms' figures are added into the surviving firm, and historical periods are restated as well.

  • Pros: no rules to extend, no extra formulas, no slower calculation.
  • Cost: the acquired firms no longer appear separately in the database; in other words, the data becomes coarser-grained.
  • Mitigation: the acquired firms' original figures stay in the source files, so they can still be looked up if really needed.

The trade-off: granularity should serve the decision

I use both approaches in practice; the second does not replace the first. The difference is not technical sophistication but what the decision needs. To decide, I ask one question first: how many firms are being merged this time?

When to useOne-to-one (1 + 1)One acquires several (1 + 1 + 1 …)
Executives' questionWhat are the figures before and after? Needed for disclosure and reconciliationWho is how big now? Is growth overstated?

System costGrows with each acquired firmAlmost unchanged

The deal has already happened. What executives care about is current size and a growth rate that isn't inflated, not exactly how big the acquired firm used to be. Making the whole system more complex and slower for a question that is rarely asked is not worth it.

In data warehousing, this is the choice between "restating history as things are now" (as-is) and "keeping history as it was" (as-was). Mature practice usually keeps both: a raw layer keeps each firm's own figures, and a reporting layer provides the restated basis. My approach works the same way: the original source files are the raw layer, and the database and reports are the restated version.

Practical reminders

  • Never discard the raw data: merging in the load layer is irreversible, and the original source files are the only way back.
  • Remember to merge every period: until the acquired firm ceases to exist legally, source data still lists it separately. A warning in the load checks helps avoid missing the merge in any month.
  • Disable flags need a reminder: a pre-registered deal "quietly stays out of the calculations", and the system raises no error. Forget to remove the flag in the effective month and the report looks perfectly normal while nothing has been merged. The checklist should list every deal that is still disabled.
  • Write the decision down: when both approaches coexist, document which companies use which approach from which period, or whoever takes over will be lost.
  • Rankings shift too: once the acquired firm disappears from history, other companies' past rankings may move up one place. This is correct on a pro forma basis, but have a one-line explanation ready for executives.

What I learned

Data completeness matters, but it is not the goal. Good data design means knowing which details deserve a place in the system, and which only need a way back.
